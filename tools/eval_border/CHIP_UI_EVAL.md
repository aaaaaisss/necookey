# 文節チップ UI の手数評価（2026-10-28、境界操作の作り直し後）

新しい候補欄（上段＝文節チップ、下段＝予測／選択チップの候補、境界は「長押し展開＋文字間タップで切る」
「チップ間タップでくっつける」「チップ端フリックで 1 字ずらす」）で誤変換を正解に直すのに何手かかるかを、
現行 UI（変換ボタンで文節区切り＋候補リスト）と比べた。モデルは `converter/candidatebar/ChipBar.kt`、設計は `docs/CHIP_BAR.md`。

## 要約
- 対象: 179 文・reg 109・dia 20 と、179 文を 2 文ずつつないだ長文 89（long.tsv）。1 位が lenient 不一致の誤り 54 文。
- **全体候補あり**（読み全体の N-best 2〜8 位を予測行から 1 手で選べる）: 誤り 54 文の平均 **新 1.17 手 vs 現行 1.28 手**
  （前版チップ UI 1.19）。短文はほぼ「全体の 2 位を選ぶ」1 手で両 UI 同じ。差が出るのは長文（1.39 vs 1.72）。
- **全体候補なし**（チップ／文節操作だけ）: **新 1.93 vs 現行 2.20**（前版 1.96）。区切り誤り **1.36 vs 2.09**（前版 1.55。新が少ない 8 文 / 現行が少ない 1 文）、
  ツギハギ 3.00 vs 3.67、同音 1.92 vs 2.00（15 / 14 で互角）。
- 到達率は 6 手以内で両 UI とも 54/54。
- 誤り 54 文の最短手順（全体候補なし）で使われた操作: 候補 44・タップ 30・左フリック 11・くっつける 11（10 文）・右フリック 8・**切る 0**。
  区切り誤りの大半はフリック 1 手（`ここでは|着物` → 左フリック → `ここで|履物`）。くっつけるは「誤って細切れになった塊をくっつけて
  候補から選ぶ」（`偉い|異なった` → くっつける → 候補 `えらいことなった`、`金橋の|橋を` → くっつける → `かな橋の端を`）で効いた。
  切るは lenient 一致の文（`ズッ友で` → `ずっ|ともで` など）でしか使われず、この評価セットでは長い塊を離れた位置で切る必要がほぼ無い。
- 前版から変わった文（4 件）: 改善 L034（全体候補あり 3→2、なし 4→2 手）・L017（なし 4→3 手）、悪化 u021（なし 1→2 手）・L011（あり・なしとも 1→2 手）。
  悪化 2 件は `ギャン|側な` の揺れ分割をやめたため `ギャン側な` 1 チップ → タップ＋候補 2 手（前版は左フリック 1 手）。
  予測行のチップ候補（chipPicks）と区切り候補の削除による悪化は無かった（タップ＋候補・フリック＋候補で同じ手数に届く）。
- 候補選択後に次のチップへ選択を自動で進める変種は手数が変わらなかった（1.17）。

## 方法
- `ChipUiEvalTest`（app/src/test/.../converter/quality）。実機既定経路 `DeviceConfigConversion`（n=8、昇格後、n-gram・人名/Wiki 辞書・ラティス表あり）
  で必要な部分読みを都度変換（同じ読みはキャッシュ）。
- 探索は `ChipUiSolvers.kt`（一様コスト探索、上限 6 手、確定は数えない）。正解の先頭と食い違う最初のチップ f と f-1 に関わる操作だけ試し、
  候補選択は正解の該当位置と一致するものだけ。正解は in.tsv の別解（`|`）のどれか（完全一致）。1 位が lenient 一致の文は 0 手扱い。
- 新 UI の操作と手数: 予測行で全体の別候補 1（最初だけ）、チップのタップ 1、候補選択（漢字候補・かな）1、
  **切る = 長押し（展開）＋文字の間タップ 2**、**くっつける（チップ間タップ）1**、チップ f/f-1 の左右フリック 1（各 1 字）。
  境界操作の後は変わったチップが選択状態（続けて候補を選べば 1 手）。初期チップは 1 位経路の文節、読み 7 字以上だけ自立語の頭で割る。
- 現行 UI の推定（各 1 手）: 変換前は全体の別候補と、上段の「最初の文節の別候補」（選ぶとその文節だけ確定し残りが新しい入力）。
  変換ボタンで文節セッション → フォーカス移動（長押し矢印）、文節の伸縮（残り全体を再変換）、区切りパターン切替、候補タップ（フォーカスまで確定）、
  スペースで候補送り（k 位は k 手）。
- 再現: `NK_CHIP_OUT=/tmp/x NK_CHIP_SETS="179=$PWD/in.tsv;reg=$PWD/reg.tsv;dia=$PWD/dia.tsv;long=$PWD/long.tsv" ./gradlew --no-daemon :app:testFullStandardDebugUnitTest --tests '*ChipUiEvalTest*'`
  → `python3 chip_eval.py /tmp/x 179=in.tsv reg=reg.tsv dia=dia.tsv long=long.tsv --classified classified.tsv --list`。文ごとの結果は `chip_eval/*.tsv`。

## 気づいた問題点
1. **評価セットが易しい**: 誤りのほぼ全部で正解が全体 N-best の 2〜8 位にあり、「全体候補あり」では UI 差がほとんど出ない。
   切る（2 手）が効く「長い塊を離れた位置で切る」誤りがセットに無く、切るの価値はこの評価では測れていない。
2. **現行 UI の「最初の文節の別候補」は強い**: 同音異義が先頭文節にあると 1 手（u001・h006・r020）。新 UI はタップ＋選択の 2 手
   （予測行にチップ候補を混ぜる案は先読み予測が隠れるので不採用）。全体候補なしの同音が互角なのはこのため。
3. **くっつける・フリックが「再変換して候補を出し直す」手段として使われる**: `体重を|図る` → くっつける → 候補 `体重を量る` のように、
   ユーザーが区切りを変えたいわけでなく候補を出し直すために使う手順が最短に出る（タップ＋候補と同手数）。探索上は正当だが、
   実機で自然に選ばれる手順かは未確認。単独再変換の揺れ（同じ区切りに戻すと表記が変わる）は remembered で抑えている。
4. **揺れ分割をやめた影響**: `ギャン側な` のように 1 位が間違っていても塊のままになる文が 1 件悪化（1 → 2 手）。
5. 長文で正解の一部が lenient 一致（かな/カナ違い）でも完全一致を目標にしているので、long の手数は両 UI とも少し多めに出る。
6. 実機の操作コスト（長押しの待ち時間、チップ間の隙間の狙いにくさ）は手数に入っていない。
