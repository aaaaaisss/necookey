## 方法
- `ChipUiEvalTest`（app/src/test/.../converter/quality）。実機既定経路 `DeviceConfigConversion`（n=8、昇格後、n-gram・人名/Wiki 辞書・ラティス表あり）
  で必要な部分読みを都度変換（同じ読みはキャッシュ）。1 位は既存ダンプと一致（179 文 lenient 158、致命 4・継接 1、ev3.py で確認）。
- 探索は `ChipUiSolvers.kt`（一様コスト探索、上限 6 手、確定は数えない）。正解の先頭と食い違う最初のチップ f と f-1 に関わる操作だけ試し、
  候補選択は正解の該当位置と一致するものだけ（直す順番は手数に影響しないため）。正解は in.tsv の別解（`|`）のどれか（完全一致）。
  1 位が lenient 一致の文は 0 手扱い。
- 新 UI の操作（各 1 手）: 予測行で全体の別候補（最初だけ）、チップのタップ、候補選択（漢字候補・かな）、区切り候補、チップ f/f-1 の左右フリック
  （フリックしたチップが選択状態になる）。初期チップは 1 位経路の文節。読み 7 字以上か、2・3 位経路が両端で区切らないチップは自立語の頭で割る。
- 現行 UI の推定（各 1 手）: 変換前は全体の別候補と、上段の「最初の文節の別候補」（選ぶとその文節だけ確定し残りが新しい入力）。
  変換ボタンで文節セッション → フォーカス移動（長押し矢印）、文節の伸縮（残り全体を再変換）、区切りパターン切替、候補タップ（フォーカスまで確定）、
  スペースで候補送り（k 位は k 手）。IMEService の挙動（resizeFocusedBunsetsuSegment・handleBunsetsuCandidateClick・TwoRowCandidateBarPlanner）に合わせた。
- 再現: `NK_CHIP_OUT=/tmp/x NK_CHIP_SETS="179=$PWD/in.tsv;reg=$PWD/reg.tsv;dia=$PWD/dia.tsv;long=$PWD/long.tsv" ./gradlew --no-daemon :app:testFullStandardDebugUnitTest --tests '*ChipUiEvalTest*'`
  → `python3 chip_eval.py /tmp/x 179=in.tsv reg=reg.tsv dia=dia.tsv long=long.tsv --classified classified.tsv --list`。文ごとの結果は `chip_eval/*.tsv`。

## 気づいた問題点
1. **評価セットが易しい**: 誤りのほぼ全部で正解が全体 N-best の 2〜8 位にあり、「全体候補あり」では UI 差がほとんど出ない。
   区切り UI の差を見るには長文（long）や N-best に正解が無い文が要る。実機で全体候補が予測行のどこに出るか（スクロール要否）も未確認で、
   現行 UI 側の 1 手は甘めの見積もり。
2. **現行 UI の「最初の文節の別候補」は強い**: 同音異義が先頭文節にあると 1 手（例 h006・h021・r020）。新 UI はタップ＋選択の 2 手。
   予測行（チップ未選択時）に「いちばん怪しいチップの候補」を数個混ぜれば同音も 1 手になる見込み。
3. **フリックで選択も兼ねる前提に依存**: 新 UI の 1〜2 手の多くが「フリック → そのまま候補／区切り候補」。フリックで選択しない設計だと +1 手。
4. **単独再変換の揺れ**: フリック後は隣接 2 チップを文脈なしで再変換するので、同じ区切りに戻しても表記が変わる（d014 は右→左フリックで 生きんさい→行きんさい）。
   探索はこれを手として使うが、ユーザーが狙ってやる操作ではない。逆に良い表記が消えることもある。
5. **揺れ判定で割ったチップが不自然**: `変える仕事`・`金橋の`・`企画|書を` のように、自立語の頭で割るだけでは意味の塊にならない場合がある。
   2・3 位の経路の区切りで割る（N-best の境界の和集合）方が自然かもしれない。
6. **区切り候補に半角カナ 1 語の経路が混ざる**（L048 `ｼｮｳﾐｲﾐﾅｲｲｹｽﾞﾔﾅｱ`）。読み全体を 1 語で覆う文字種変換は区切り候補から外すべき。
7. 長文で正解の一部が lenient 一致（かな/カナ違い）でも完全一致を目標にしているので、long の手数は両 UI とも少し多めに出る。
